# 多视频平台账号运维 · 设计与路线图

> 目标：让 AstrBot 具备**多视频平台账号的完整运维能力**（登录、续期、多账号、风控、资料、作品、评论、数据），
> 以及**主动浏览、评论、下载发给用户**的能力；面向小白用户，一切都能用自然语言完成，危险操作必须经管理员批准。
> 后期与视频生成插件联动，形成“生成 → 审核 → 发布 → 互动 → 复盘”的闭环。

本文档描述 v0.9 的现状、整体架构、分阶段计划和对外接口约定。

---

## 1. 设计原则

1. **小白优先**：默认不依赖任何额外付费模型（Gemini / MiMo 默认关闭），看图和总结都交给用户已经在用的对话模型（如 DeepSeek）；
   配置用自然语言完成（`video_plugin_settings`），体检告诉用户还缺什么；审批可以直接回复「确认 1234」。
2. **安全第一**：所有写操作只能“提交申请”，批准必须是管理员本人发出的消息；没有任何工具能代为确认。
   普通用户的申请推送到管理员审批会话，结果回告申请人。
3. **省上下文、保缓存**：工具少而精（5 个按 action 路由），描述静态不含动态内容；工具结果只返回必要字段。
4. **抗风控**：请求节流、账号级额度、风控熔断、内容去重；能用官方 Web 接口就不用浏览器自动化，必须用浏览器时模拟真人。
5. **平台可插拔**：新平台只实现 `CreatorPlatform` 适配器，命令、审批、LLM 工具、浏览流程全部复用。

## 2. 架构

```
LLM 工具层 (tools/ops_tools.py)        video_browse · video_download · video_account · video_action · video_plugin_settings
命令层     (handlers/*)                /bili_* /va_* /dy_* 「确认 1234」
───────────────────────────────────────────────────────────────────────────────
审批层     (services/creator_ops.py)   PendingOp：记录申请人/账号/内容 → submit 推送 → 管理员确认 → _execute
审计       (services/audit_log.py)     每个 PendingOp 的 created / approved(结果) / rejected / expired / dropped → audit.jsonl
浏览理解层 (services/browse_service)   转写(字幕/线上ASR/STT/本地) → 按转写挑帧 → 对话模型看图总结 → 缓存
下载分发层 (services/deliver_service)  下载 → 按大小发视频/文件 → 定时清理
设置层     (services/settings_service) 中文设置目录 · 模糊匹配 · 体检 · 预设
账号层     (services/account_manager)  当前账号/账号池 · 续期 · 巡检 · 轮换 · 风控熔断 · 告警推送
风控工具   (creator/human.py, bili_account) 频率闸门 · 人类化交互 · bili_ticket/WBI · 去重 · 链接拦截
───────────────────────────────────────────────────────────────────────────────
平台适配层 (services/creator/*.py)     CreatorPlatform: douyin.py · bilibili.py · (kuaishou / xhs / channels / youtube …)
```

### 2.1 平台适配器接口（`services/creator/base.py`）

| 方法 | 说明 | 是否必须 |
|------|------|----------|

| `list_works(limit)` / `resolve_work(ref)` / `work_context(id)` | 作品列表 / 链接→ID / 标题、作者、时长 | 必须 |
| `list_comments(id)` / `reply_comment(id, cid, text)` | 读评论 / 回复 | 必须 |

| `fetch_video(id, ctx, max_seconds)` | 下载（长视频只取开头） | 浏览需要 |
| `upload(path, title, tags, **opts)` / `delete(...)` | 发布 / 删除（opts 为平台参数，如 B站 cover/tid/desc） | 可选 |
| `feed()` / `search()` / `hot_comments()` / `report_watch()` | 浏览类（抖音另有 `hot_words()` 热搜词） | 可选 |
| `profile()` / `update_sign()` / `update_avatar()` | 资料 | 可选 |

## 4. 分阶段计划

### P1 · 基础运维补齐（v0.9 已完成主体）
- ✅ **抖音浏览**：推荐流（`tab/feed`）/ 热搜词（`hot/search/list`）/ 搜索（`search/item`，需登录），全部走 BrowserSigner 页面内 fetch 签名
- ✅ **抖音发评论、改签名/头像**：评论走 `comment/publish`；资料走个人主页"编辑资料"弹窗（提交接口 `commit/user`）。
  实测：新设备上的抖音写操作都会弹"短信验证码 / 原设备扫码"，插件识别后点取消退出（不触发短信），提示管理员扫一次码；验证后评论、签名、头像均可正常执行
- ✅ **B站投稿**：`preupload` → upos 初始化（需带 `filesize/partsize/biz_id`）→ 分片 PUT → 合并 → 封面上传 → `add/v3`；封面、分区、标签
- ✅ **操作审计**：`audit.jsonl` 记录申请人、批准人、执行结果、失败原因；`/va_audit`、`video_account audit`、WebUI 接口 `audit`
- ⏳ 抖音改昵称、B站定时发布（`dtime`）
- ⏳ **设备验证引导**：检测到抖音"本人验证"时，把"原设备扫码"二维码推给管理员（目前需要人工操作一次浏览器）
- ⏳ **B站删稿**：短信验证码由管理员回传（`340022`），或引导到 App 删除
- ⏳ **审批体验**：WebUI 审批页（列表 + 一键批准/拒绝 + 审计列表）；批量审批；审批超时提醒
- ⏳ **账号健康分**：综合登录有效期、近 24h 风控次数、写操作成功率（审计日志已提供数据），低分自动降权/暂停

### P2 · 多平台
| 平台 | 登录 | 读 | 写 | 难点 |
|------|------|----|----|------|
| 快手 | 扫码（Web） | 作品、评论 | 回复、发布 | 签名参数 |
| 小红书 | 扫码（Web） | 笔记、评论 | 回复、发布图文/视频 | x-s 签名、风控严格，优先浏览器方案 |
| 视频号 | 扫码（助手后台） | 作品、评论 | 回复、发布 | 只有创作者后台，页面自动化 |
| YouTube / TikTok | OAuth / Cookie | Data API | 回复、上传 | 海外网络与配额 |

每个平台：先做只读 + 回复评论，再做发布；统一走 `CreatorPlatform` 与审批层。

### P3 · 内容运营
- **定时发布 / 内容日历**：发布申请可带计划时间，批准后进入队列，到点发布并回报结果
- **数据看板**：播放、点赞、粉丝、互动率按日采样，`/va_report` 周报；LLM 可读取摘要做复盘建议
- **评论巡检策略**：定时扫描新评论，按策略（关键词、高赞、粉丝等级）起草回复，打包成一次审批
- **私信与粉丝**：私信读取与回复（同样需要审批）、关注/取关管理

### P4 · 矩阵与安全
- **账号隔离**：每个账号独立代理、UA、浏览器配置目录（防关联）
- **审批分级**：低风险操作（如观看上报、点赞）可配置为免审或额度内自动通过；发布、删除、改资料始终必审
- **风控画像**：记录每个平台的风控码与触发频率，自适应调整节流参数

## 5. 与视频生成插件联动

目标闭环：**生成 → 审核 → 发布 → 互动 → 复盘**。提供三种接入方式，按耦合度由低到高：

1. **LLM 工具链（零耦合，推荐先用）**：生成插件的工具返回视频文件路径/直链，LLM 再调用
   `video_action(action="upload", target=<路径或直链>, text=<标题>, tags=...)`；审批照常进行。
2. **插件间直接调用（已提供）**：
   ```python
   star = self.context.get_registered_star("astrbot_plugin_videos_analysis")
   res = await star.star_cls.publish_request(event, "/abs/path/out.mp4", "标题", ["话题"], platform="douyin", account="主号")
   # res["status"]: pending_confirmation / pending_admin_approval / rejected
   ```
   本接口保证向后兼容；发布结果会推送到申请所在会话。
3. **投递目录（计划中）**：生成插件把成品与 `meta.json`（标题、话题、平台、账号、计划时间）放入
   `data/plugin_data/astrbot_plugin_videos_analysis/inbox/`，本插件巡检时自动生成发布申请。

**素材校验（计划中）**：发布前按平台规范检查时长、分辨率、码率、文件大小、封面比例，不合规直接在预览里提示。
**复盘回流（计划中）**：发布后的播放/评论数据可提供给生成插件，作为下一轮选题与脚本的参考。

## 6. 上下文与缓存（评估结论，v0.8 实测）

| 项目 | v0.7 | v0.8 |
|------|------|------|
| 工具数量 | 16 | 5 |
| 工具 schema（o200k 估算） | ≈1974 tokens | ≈931 tokens（v0.9 加浏览平台参数与 audit 后 ≈1000） |
| `watch` 结果 | 概要 + 1500 字转写节选 + 热评 | 概要 + 3 条热评（转写不进上下文） |
| 评论列表 | 最多 40 条 × 200 字 | 最多 20 条 × 80 字 |
| 设置列表 | — | 仅在调用 `show` 时返回；找不到设置时只返回 3 个候选 |

- AstrBot 会把工具结果写入对话历史并在之后每轮重发，因此**结果体积比 schema 更重要**；长内容（转写、帧）只在插件内部使用，不回传给模型。
- 工具描述为静态文本：不随用户、账号、配置变化，**请求前缀稳定，不会破坏 DeepSeek 等模型的前缀缓存**。
  动态信息（账号名、配置值、额度）一律通过工具结果按需获取。
- AstrBot 的工具权限只在调用时检查，所有用户看到同一套工具定义，这对缓存也是有利的。
- 单次工具结果超过约 2.75 万 tokens 时 AstrBot 会自动转存文件；本插件的结果远低于此阈值。

## 7. 风险与合规
- 平台规则：自动化操作可能违反平台用户协议，默认频率保守、写操作全部需人工批准；请仅用于自有账号。
- 凭据安全：cookie、refresh_token、API Key 只保存在本地 `plugin_data`；展示时一律打码；建议管理员私聊配置密钥。
- 用户授权：普通用户只能发起申请，不能直接动用机器人账号。

## 8. 测试策略
- 每次改动在临时 `qqsum-astrbot:playwright` 容器中测试，绝不在线上 bot 上测试；
- 用真实对话模型（如 deepseek-v4.1-flash）跑自然语言用例：浏览、下载、配置、审批（含非管理员路径）；
- 写操作只在自己的稿件上测试，测试后删除；签名等资料改完即改回。
- v0.9 实测记录（测试容器 + deepseek-v4.1-flash）：抖音推荐/热搜/搜索/按序号观看、抖音评论（发后删除）、签名与头像（改后改回）、
  B站 23MB 视频 3 分片投稿成功；B站删稿因短信验证码失败，需手动删除；审计覆盖成功/失败/拒绝/过期。
